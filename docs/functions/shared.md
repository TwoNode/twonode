## `lib/push/` — push notifications to the mobile app (TASK-0015 1I)

Off unless `PUSH_ENABLED=1` (see `.env.example` §11): with it unset nothing here sends or looks anyone up. **The text a push shows is fixed and generic** (TASK-0006 P6-D3): a lock screen shows it to whoever holds the phone, so it never carries a plan title, a reviewer's comment, a place, a name or a number. The app opens the plan from `data.planId` and shows the detail inside the app.

| File              | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `deviceTokens.ts` | The `DeviceToken` table's functions. `registerDeviceToken(userId, platform, {deviceId, token, os, appVersion})` keeps a token only for a `deviceId` that is a **live device session of that user** (an unrevoked, unexpired `RefreshToken` with that `deviceId`) and returns `false`, writing nothing, otherwise; in one transaction it deletes any row with the same token (whoever's: a phone someone else signs in on moves to them) or the same user and device (a changed token replaces the old one), then writes the pair. `removeDeviceToken(userId, platform, deviceId)`, `tokensForUsers(userIds, platform)` (returns only `{userId, token}`, and only for a device whose session is still live: a token whose user has no unrevoked, unexpired `RefreshToken` with that `deviceId` is not returned and is deleted by row id, best effort and never logged, so a phone that signed out with no connection stops getting pushes; app issue A-053), `removeTokens(tokens)` (dead ones, as a send's ticket reported them), `removeTokensDeadSince([{token, sentAt}])` (dead ones as a delivery receipt reported them, 1I.6: deletes a token only if it was last seen no later than the send the receipt is about, so an install that registered again since is kept; in chunks of 500). `EXPO_TOKEN` is the pattern a token must match (`ExponentPushToken[...]`). A token is a delivery address, not a credential, but it is never returned to a client or logged. |
| `sender.ts`       | `PushSender` (`enabled`, `send(messages)` returning one ticket each, never throwing), `NullPushSender` (does nothing), `ExpoPushSender` (Expo's push service: batches of 100, a 5 second timeout per request, optional `Authorization: Bearer` from `EXPO_ACCESS_TOKEN`, `DeviceNotRegistered` becomes `unregistered: true`, a short or failed answer becomes an error ticket for the messages it covers; an accepted ticket carries Expo's receipt `id`), `receipts(ids)` (up to 1000 ids per call to Expo's `getReceipts`: a `Map` of id to `PushReceipt` for the ids that have one, an empty map for no ids, and **`null` when Expo could not be asked**, which says nothing about any id; `NullPushSender` answers an empty map), `getPushSender(env)` (on only when `PUSH_ENABLED === "1"`). The rest of the server talks to the interface only, so FCM and APNs directly can replace Expo later.                                                                                                                                                                                                                                                                                              |
| `pushEvents.ts`   | `PushKind` (`PLAN_QUERIED`, `READY_FOR_PHYSICAL`, `PLAN_SHARED`, `PLAN_LODGED`, `SUBSCRIPTION_ENDING`, `WITHDRAWAL_UPDATED`: one kind, with no amount, bank or reason, for a withdrawal paid or refused; each belongs to one switch, see `preferences.ts`), `buildPushMessage(token, event)` (fixed copy; `data` is `{v: 1, kind, planId?}` and nothing else; a `planId` that is not a uuid is dropped; Android channel `updates`) and `sendPush(userIds, event, sender?)`: does nothing when push is off or nobody registered, sends one push to each registered phone of these people (Surfboard), deletes the tokens the service says are dead, keeps the receipt id of each message the service took (`recordTickets`, so the receipts can be read later), **never throws** (a notification must not break the action that caused it) and returns how many pushes the service took. Before looking up any phone it leaves out the people who switched this kind off or are in quiet hours (`usersWhoWant`), and after finding phones it sends each person at most one push of a kind in 5 minutes (`claimPushWindow`); a failure of either check means no push, never a guess.                                                                                                                                                                                                                                                                                        |
| `receipts.ts`     | Delivery receipts (TASK-0015 1I.6). Accepting a message (the ticket) does not say Google or Apple took it; the receipt, about 15 minutes later and cleared after 24 hours, does, and it is where an uninstalled phone shows up as `DeviceNotRegistered`. `recordTickets([{ticketId, token}])` keeps accepted tickets in `PushReceiptTicket` (once each; **never throws**; logs a count only, never a token or the database's own message). `checkPushReceipts(sender?, now?)` takes up to 5000 tickets at least 15 minutes old, oldest first, asks for their receipts 1000 at a time, deletes the tokens `DeviceNotRegistered` names (through `removeTokensDeadSince`), counts and logs every other failure by its error (`InvalidCredentials` and `MismatchSenderId` at `error` level because every push is failing, the rest at `warn`; a gone phone is ordinary and only counted), and forgets a ticket once its receipt is read or when it is more than 24 hours old with none. If Expo cannot be asked it stops, forgets nothing and leaves the rest for the next run; a database failure throws before the tickets are forgotten (at-least-once, safe to repeat). Does nothing when push is off. Returns `{checked, delivered, failed, removedTokens, expired, deferred}`. Run by `/api/cron/push-receipts` (guarded by `CRON_SECRET`, daily at 10:00 UTC; a Pro plan can run it hourly, a Hobby plan cannot), which then also deletes cool-down rows over a day old (`prunePushCooldowns`) and answers `{...counts, prunedCooldowns}`. |
| `preferences.ts`  | What a person wants pushed (TASK-0015 1I.4, 1I.5), kept in `PushPreference` (one row per person and platform, written only when they change something; **no row = the defaults**: everything on, no quiet hours). `PUSH_CATEGORIES` (`PLANS_NEED_YOU`, `PLAN_LODGED`, `PLAN_SHARED`, `SUBSCRIPTION`, `WITHDRAWALS`) and `CATEGORY_OF_KIND` (a `Record` over every `PushKind`, so a new kind cannot be added without choosing its switch; `PLAN_QUERIED` and `READY_FOR_PHYSICAL` share `PLANS_NEED_YOU`). The row stores what is switched **off**, so a switch added later is on for everyone. `getPushPreferences(userId, platform)` (defaults when there is no row; a read writes nothing), `pushPreferencesPatch` (zod: only what changes; `categories` and `quietHours` each with any of their fields; unknown keys, a time that is not `HH:MM`, a time zone `Intl` does not know and an empty change are refused), `applyPatch(row, patch)` (pure merge), `updatePushPreferences(userId, platform, patch)` (merges onto the stored row, refuses **quiet hours that start and end at the same minute** with a 400, upserts, answers everything as it now stands), `inQuietHours(now, row)` (hours may run through midnight; the start minute is quiet, the end minute is not; read in the row's IANA zone through `Intl`; a zone it cannot read counts as **not** quiet), `usersWhoWant(userIds, kind, platform, now?)` (one query; a person with no row wants everything). Served by `GET` and `PATCH /api/v1/surfboard/push/preferences` (role USER; PATCH checks the origin like every cookie-capable write). |
| `cooldown.ts`     | At most one push of a kind to a person in a 5 minute window (TASK-0015 1I.4): `claimPushWindow(userIds, kind, now?)` writes a `PushCooldown` row whose id is `userId:kind:window` with `skipDuplicates`, so the claim is a unique-key write and atomic across servers with no lock (checked with 25 parallel claims on a real Postgres: exactly one wins); it answers the people whose window was free. Two pushes either side of a window boundary can both be sent. `prunePushCooldowns(now?)` deletes windows over a day old (run by the receipts cron). |

## `lib/mobile/` — the mobile API contract (TASK-0015 1C)

What the app is promised, written once: see [`docs/mobile/api-contract.md`](../mobile/api-contract.md). Not a runtime dependency of any route; it is read by the tests, `npm run docs:openapi` and `npm run contract:live`.

| File                         | Description                                                                                                                                                                                                                                                        |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `contract/schemas.ts`        | One zod 4 schema per answer (`PlanSummaryData`, `PlanDetailData`, `PlanStatsData`, `MeData`, ...), `envelope(data)` for `{ success: true, data }` and `ErrorBody` for the failure envelope. Its last lines make `tsc` fail if a schema and the service's return type stop agreeing. |
| `contract/endpoints.ts`      | `ENDPOINTS`: one entry per operation (method, path, `access`, `versionGate`, query parameters with an example each, request body with a valid example and invalid ones, the `data` schema, failures, the route file).                                                  |
| `contract/errorCodes.ts`     | `ERROR_CODES` (status, meaning and what the app does for every code it reacts to) and `UNCODED` (failures that carry no code).                                                                                                                                       |
| `contract/openapi.ts`        | `buildOpenApiDocument()` builds the OpenAPI 3.1 document; `OPENAPI_VERSION` is bumped by hand (major for anything an installed app could break on, minor for what it can ignore).                                                                                    |

`scripts/mobile/contract-live-check.ts` (`npm run contract:live`, read only) signs in to a running server (`API_BASE`, `CHECK_EMAIL`, `CHECK_PASSWORD`) and checks every read route's answer against these schemas.
