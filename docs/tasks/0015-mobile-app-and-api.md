## 1. Objective

Ship a native companion app for Surfboard surveyors (Android and iOS) that lets them **access, monitor and act** while away from the desk: Plans, Records (batches), Stats, Home (map and search), Profile. Creating records, CAD/PDF upload, geometry verification, record-copy batch preparation and payment, and admin work stay on the web. The app talks to the existing `/api/v1/*` contract and must not care which backend answers it ([roadmap rule](../mobile/roadmap.md)).

**Product scope in one line per tab (from the brief):**

| Tab                  | What it does                                                                                                                                                                                  |
| :------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Home**             | Map of the surveyor's own plans, one search box (plan number, pillar number, title, facilitator, locality, LGA, coordinate, address), current location, record details sheet, navigate to it. |
| **Plans**            | All, Shared, Queried. Badge when any plan is queried; a queried plan explains which stage queried it, why, and the history.                                                                   |
| **Records** (centre) | Batch cards with per-status counts, batch and record status, search, "Physical Copies Submitted" action (disabled when nothing is ready), history once every plan is lodged.                  |
| **Stats**            | Total, lodged, queried; by facilitator and by LGA/LCDA/ward; active batches; wallet and earnings; tap a figure to open the records; date filter on `surveyPlanDate`.                          |
| **Profile**          | Account and firm, wallet, subscription status (no purchase on iOS), settings, signed-in devices, support, sign out.                                                                           |

### 1A. Native auth (the one hard blocker) · Size L

Today: access token is a 15-minute JWT in an httpOnly cookie, the refresh token is a cookie scoped to `/api/v1/auth/refresh`, and `withAuth` reads only cookies. There is no `Authorization: Bearer` path, so every authenticated call from a native client returns 401. CSRF (`lib/auth/csrf.ts`) also rejects any mutating request without a matching `Origin` or `Referer`.

- [x] 1A.1 `POST /api/v1/auth/mobile/login`: email, password, `platform: "surfboard"`, device label and id; returns `{accessToken, refreshToken, expiresIn, user}` in the body. Reuse `issueSession` internals and the same bcrypt check; no cookies set. **Done 2026-10-19** (PR #495, branch `feat/mobile-auth-bearer`): `POST /api/v1/auth/mobile/login`, body session, `Cache-Control: no-store`, no cookies.
- [x] 1A.2 `POST /api/v1/auth/mobile/refresh`: takes the refresh token in the body, rotates it. **Re-rotate inside the 30-second grace window** (revoke the live successor and return a fresh pair in the same family) so a lost response does not log the user out (`rotateRefreshToken` today returns only an access token there, and treats a later re-presentation as reuse and revokes the family). **Done 2026-10-19:** rotation shared with the web (`rotateCore`); grace-window re-rotation; 409 `REFRESH_CONFLICT` on a race.
- [x] 1A.3 `POST /api/v1/auth/mobile/logout`: revokes that device's token family. **Done 2026-10-19:** revokes the device's family; always 200.
- [x] 1A.4 Bearer branch in `getServerSession` (`lib/auth/session.ts`) and therefore in `withAuth`: if `Authorization: Bearer` is present, verify it exactly as the cookie token (signature, expiry, `platform` claim). Cookie path unchanged. **Done 2026-10-19:** bearer is the only credential when present; a bad bearer never falls back to cookies.
- [x] 1A.5 **Bearer-aware CSRF:** a request that authenticates through `Authorization: Bearer` skips the Origin/Referer check. Cookie-authenticated requests must still be checked. ### 1B. Version gate and client identification · Size S

> **Built 2026-10-25 (draft API PR #511, branch `feat/mobile-version-gate`, stacked on docs PR #510): the version gate (1B) and the emergency sign-in switch (the first half of 1J.3).** Nothing changes until an admin sets something: the defaults are no minimum and sign-in on.
>
> - **Where it is kept.** In the Surfboard settings row, under `mobileApp`: `minimumAndroidVersion`, `minimumIosVersion`, `androidStoreUrl`, `iosStoreUrl`, `signInEnabled`. Changed with `GET` and `PATCH /api/v1/surfboard/settings/mobile-app` (Surfboard `ADMIN` or `SUPERADMIN`; a new settings version and an `UPDATE_MOBILE_APP_SETTINGS` audit entry each time). No deploy. A server instance reads the row at most once a minute (the instance that took the `PATCH` at once), so a change reaches every instance within a minute. Saving, resetting or reverting the other settings on the web page never touches these five values.
> - **The gate** (`lib/api/mobileApp.ts`). A request is a mobile request when it carries `Authorization: Bearer` or `X-App-Platform`; website traffic carries neither and never meets it. With a minimum set for a store, a request from that store whose `X-App-Version` is older, missing or not a version is refused with **`426 APP_UPDATE_REQUIRED`**, `details: { platform, minimumVersion, storeUrl }`. A request that does not say which store it comes from is refused too while any minimum is set (the app always sends both headers). A store with no minimum of its own is never held back. A minimum that is not a version ("latest") is ignored and logged, so a typo cannot lock everybody out. Versions are compared as numbers (1.10.0 is newer than 1.9.0).
> - **The switch.** `signInEnabled: false` makes `POST /auth/mobile/login` answer **`503 MOBILE_SIGN_IN_DISABLED`**. Sessions that are already open carry on: refresh is not stopped by it.
> - **Where it applies.** In `withAuth` (before the session is read, so an old app is told to update rather than sent round a refresh), on `GET /auth/me` (the one route the app calls that is not behind `withAuth`; mobile requests only), and directly in mobile login and refresh. **Deliberately exempt:** `mobile/logout` (an old app may always sign out) and `mobile/request-password-reset`.
> - **Fails open.** When the settings cannot be read nothing is refused and sign-in stays on: a database hiccup must not turn into an app nobody can use. A failed read is not cached.
> - **Found on the way:** the web page's "Reset to default" and "Revert" write a whole settings row, which would have lifted a forced update or re-opened sign-in during an emergency. Both now keep the stored `mobileApp`; two tests pin it.
> - **Checked:** 92 new tests in 6 files (the gate's rules and cache, `withAuth` order and reach, login, refresh, logout and `/me`, the settings service, and the admin route's roles, CSRF and validation); each of 33 deliberate breaks of the gate, the wiring, the settings and the route made a test fail. Live, against a throwaway PostGIS database over HTTP (see the log in section 14).
> - **A contract the app broke, found by looking at it (app PR #16, A-050 there):** **every** app call must carry `X-App-Version` and `X-App-Platform`, sign-in and refresh included. Until that PR the app's own auth calls sent neither, so any minimum would have refused every build at sign-in, the newest too; the live check below missed it because its script sent the headers itself. **Do not set a minimum until a build with the app's update screen (and this fix) is released:** an older build shows an ordinary error and no way forward.
> - **Not built:** a _recommended_ version (a gentle nag; it needs a design in the app), a card for these controls on the web Settings page (today an admin uses the call below), and a build of the app that has the update screen (app draft PR #16 in `TwoNode/twonode-mobile`).
>
> **Runbook (1J.3): force an upgrade, or pause mobile sign-in.** Sign in to the web admin as a Surfboard `ADMIN` or `SUPERADMIN`, open any restricted page, and run in the browser console (same origin, so the cookie and the CSRF check are satisfied):
>
> ```js
> await fetch("/api/v1/surfboard/settings/mobile-app", {
>   method: "PATCH",
>   headers: { "content-type": "application/json" },
>   body: JSON.stringify({
>     minimumAndroidVersion: "1.2.0", // "" lifts the minimum
>     androidStoreUrl: "https://play.google.com/store/apps/details?id=…", // https only, or ""
>     // signInEnabled: false,          // true again when it is safe
>   }),
> }).then((r) => r.json());
> ```
>
> Send only the keys to change; an empty body, an unknown key, a version that is not `1`, `1.2` or `1.2.3`, or an address that is not `https` is a `400` and changes nothing. To check: `GET` the same address, then sign in from an app older than the minimum and expect `426`. To undo, send `""` and `true`. Never set a minimum above the newest version that is in the store: every installed app would be told to update to something that is not there. Pausing sign-in does not end open sessions; to end a person's session use their device list.

- [x] 1B.1 Require `X-App-Version` and `X-App-Platform` on mobile routes; a server-side minimum version returns `426`-style `APP_UPDATE_REQUIRED` with a store link. **Done 2026-10-25** (draft API PR #511): required while a minimum is set (a mobile request without them gets `426`); with no minimum set nothing is required, so shipping it changes nothing.

## 13. Risks to watch

- Refresh-token loss on flaky networks (handled by 1A.2 and 2.7; test it on purpose).
- Map tile and geocoder licensing (D3); do not reuse the web map's tile sources.
- App-store review: no purchase calls to action on iOS, a working demo account, and a privacy policy.
- Store account lead times (D2, D11).
- Scope creep: the brief's exclusion list is its main strength; offline sync, uploads and admin screens stay out of v1.
- Email-verification enforcement turning on later without the app handling it (1A.8 and 3.2 cover it).
