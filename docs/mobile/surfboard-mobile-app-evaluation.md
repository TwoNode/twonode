## 1. What the brief asks for

**Principle:** Web = _Create. Process. Manage._ Mobile = _Access. Monitor. Act._ — "what does a surveyor need to access or do when away from their computer?". The app must not be a cramped port of the desktop.

| Tab (centre = Records)  | Requirements                                                                                                                                                                                                                                                                                                                                               |
| :---------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Home**                | Opens to a map with a Bolt-style prompt ("What plan? / Looking for?"). Search by `planNumber`, `pillarNumber`, `surveyName`, facilitator, locality, LGA, date. Map: see records, **search by address**, locate by coordinate (`552445,712526`, decimal lat/long, DMS), current location, select a record → details, **navigate** (in-app and Google Maps). |
| **Plans**               | All Plans · Shared Plans · Queried Plans. A **badge** (`Plans ①`) when any plan is queried. A queried plan explains _which record, why, at what level, any history_.                                                                                                                                                                                       |
| **Records** (= Batches) | Batch cards with per-status counts ("1 Ready for Physical Submission · 2 Surcon, Account Approved · 1 Queried · 1 Lodged"), batch-level _and_ record-level status, search. **"Physical Copies Submitted"** button: disabled when nothing is ready; tapping auto-selects ready records. A batch moves to history once all its plans are Lodged.             |
| **Stats**               | Total/Lodged/Queried plans, records by facilitator and by LGA/LCDA/ward, active batches, wallet/earnings; tapping a metric drills to the records; filter by `surveyPlanDate`.                                                                                                                                                                              |
| **Profile**             | Account + firm, wallet (balance/earnings/transactions), subscription (plan, billing), settings, support. Account management only — no operational workflows.                                                                                                                                                                                               |
| Out of scope on mobile  | Creating records, DWG/PDF/CSV upload, geometry verification, preparing/paying record-copy batches, detailed editing and admin — all stay on web.                                                                                                                                                                                                           |

The brief is deliberately small and well-bounded. Its biggest strength is the exclusion list; most risk in the engineering plan comes from adding things the brief didn't ask for (§4.8).

## 3. Authentication — the real blocker, and what the plan misses

Confirmed in code: `withAuth` → `getServerSession(platform)` reads **only** `access_token_<platform>` (httpOnly, `sameSite: lax`) from cookies (`lib/auth/cookies.ts`); the refresh token cookie is scoped to `path=/api/v1/auth/refresh`. There is no `Authorization: Bearer` path anywhere, so every authenticated call from a native client would return 401.

**Plan B's fix is right in outline** — add a bearer path to `withAuth`/`getServerSession` and mobile login/refresh endpoints that return tokens in the body, tokens kept in Keychain/Keystore. These points are missing or wrong:

1. **CSRF is stricter than Plan B says.** `validateCSRF` (`lib/auth/csrf.ts`) requires an `Origin` _or_ `Referer` host that matches the request host, and returns **false when both are absent** — so every mutating route (physical-copy, share, etc.) returns 403 to a native client, not just those that "check origin". Rule to implement: a request that authenticates via `Authorization: Bearer` is exempt from the Origin/Referer check. This is safe: a browser cannot attach a custom `Authorization` header cross-site without a CORS preflight, which these endpoints don't grant. It must **not** exempt cookie-authenticated requests.
2. **Refresh rotation has a lost-response problem on mobile.** The hardened refresh (`rotateRefreshToken`, `docs/auth/technical.md` §1.4) claims the old token and creates the successor in one transaction; a re-presented old token within **30s** gets an _access token only_ (the successor's raw value is never recoverable — only its hash is stored); beyond 30s it is treated as reuse and **revokes the whole family**. On the web the browser keeps whichever cookie won. On a phone, if the response carrying the new refresh token is lost (tunnel, flaky data — normal in the field), the app still holds the old token: it gets one 15-minute access token from the grace branch, then its next refresh is a "reuse" → family revoked → forced re-login. Fix in the mobile refresh endpoint: when the old token is re-presented inside the grace window, **re-rotate** (revoke the live successor and issue a fresh pair in the same family) and return the full pair. On the client: write the new refresh token to secure storage _before_ using the new access token, and run refresh through a **single-flight** guard so concurrent requests on app resume share one refresh.
3. **IP-based rate limits will hurt mobile users.** Login is keyed `ip:email`; registration sends are `register-send:<ip>` (5 per 5 minutes) and completion `register-complete:<ip>`. Mobile carriers commonly put many subscribers behind one NAT address (carrier-grade NAT — an inference from how mobile networks generally work, not something measured here), so legitimate users can exhaust a shared bucket. For mobile endpoints key limits on `(email)` and a device identifier as well, and avoid IP-only buckets.
4. **The email-verification gate applies.** When a platform enables enforcement, `withAuth` throws `EmailVerificationRequiredError` (403, code `EMAIL_VERIFICATION_REQUIRED`) for unverified users (`lib/api/withAuth.ts`). The app needs an OTP-entry screen and must treat that code as "show verification", not "error". The LINK method opens a web page — decide how it deep-links back.
5. **Platform scoping.** Access tokens carry a `platform` claim; the mobile endpoints must keep passing `platform: "surfboard"` and `withAuth` must keep checking it (already does).
6. **Device sessions.** Add a device label to the refresh-token row so a stolen/lost phone can be revoked individually (`revokeUserSession` currently revokes by user/platform), and surface "signed-in devices" in Profile.

Suggested surface (additive, web path untouched): `POST /api/v1/auth/mobile/login`, `POST /api/v1/auth/mobile/refresh`, `POST /api/v1/auth/mobile/logout`; bearer branch in `getServerSession`; bearer-aware CSRF; a `X-App-Version` header with a server-side minimum-version check for forced upgrades.

### 4.3 Coordinate conversion: the maths is fine, the labels and plumbing are not

- Plan B defines `EPSG:26391` as "Minna / UTM Zone 31N" and `EPSG:26392` as "UTM Zone 32N". **They are not.** EPSG:26391 is _Minna / Nigeria West Belt_ (a Transverse Mercator with latitude of origin 4°, central meridian 4.5°, scale 0.99975, false easting 230,738.26 m) and 26392 is the Mid Belt ([EPSG:26331](https://spatialreference.org/ref/epsg/26331/), [EPSG:26391](https://spatialreference.org/ref/epsg/26391/)). **Minna / UTM zone 31N is EPSG:26331** and zone 32N is **26332**. The repo already uses the right one: `proj4.defs("EPSG:26331", "+proj=utm +zone=31 +ellps=clrk80 +towgs84=-92,-93,122,0,0,0,0 +units=m +no_defs")` in `MaplibreMap.tsx`/`MaplibreMultiPlans.tsx`, and `convertCoordinates` defaults to 26331.
- The `+proj` string Plan B writes is numerically the same UTM definition (spelling out the Clarke-1880-RGS axes); the codes attached to it are wrong. **Verified:** the brief's own example `552445, 712526` converts to **6.4470° N, 3.4735° E** with either definition — central Lagos, as the brief intends.
- Plan B's `parseCoordinatesToLatLng` only ever uses zone 31. That's right for Lagos (the MDA is the Lagos State Surveyor General) but the Association feature introduces surveyors from every state, and **east of 6° E the plan data is zone 32**. Decide the zone from the plan's own stored location/state or prompt, not a hard-coded constant.
- `proj4` is **already a dependency** (`package.json`), and the codebase has _two_ projection paths (proj4 in the map components; ArcGIS `projectOperator` in `surfboardUtils.convertCoordinates`). Extract one shared, tested util (`lib/geo/…`) used by web and mobile instead of adding a third.
- Parsing: the UTM regex (`\d{6}, \d{6,7}`) collides with other 6-digit pairs; require a visible disambiguation (the omnibar should show "interpreted as UTM 31N → 6.447, 3.473" for confirmation) and add DMS/decimal tests, including `6°32'05.7"N 3°20'55.2"E` and 15-digit decimals from the brief.

### 4.4 Maps and tiles — a licensing problem the plan does not see

The existing web map (`MaplibreMap.tsx`) loads **`a.tile.openstreetmap.org` raster tiles** and the **unofficial Google tile endpoint `mt1.google.com/vt/lyrs=…`** (Satellite, Hybrid, Terrain, Roadmap) directly.

- **Google:** the Maps Platform terms forbid accessing map tiles or imagery "through interfaces or channels (including undocumented Google interfaces) other than the Maps API(s)" and bulk-downloading tiles ([Google Maps Platform terms](https://cloud.google.com/maps-platform/terms); wording confirmed from a search excerpt — re-read the current terms before relying on it). Hitting `mt1.google.com` from a commercial product is outside those terms.
- **OpenStreetMap:** the public tile servers are not a free CDN. Heavy use of `tile.openstreetmap.org` is prohibited without permission; apps must send a distinct `User-Agent`; **pre-seeding areas / building offline archives is forbidden**; and the policy applies "whether distributing through app stores or otherwise" ([OSMF tile usage policy](https://operations.osmfoundation.org/policies/tiles/)).

This is a risk **today** on the web; copying the same tile sources into a store-distributed app makes it a store-review and legal risk too, and rules out the "offline cached tiles" feature on those sources. Plan B's instinct (own/hosted vector tiles, Google only for external navigation deep-links) is correct but it never notices the existing problem, never prices a **satellite imagery** source (surveyors will expect satellite; that is a licensed product), and doesn't cover **address geocoding** at all — which the brief requires ("Search with address"). Decisions needed: basemap provider/hosting, imagery licence, geocoder (and its usage terms), and a fix for the web map.

_Related:_ the NIPOST postcode API (`docs.postcode.gov.ng`) offers free postcode **autocomplete** that could feed the app's "Looking for?" box for users who already know a code, but it does not return coordinates for a postcode on the free tier and is not a replacement for the geocoder decision above — see [`../integrations/nigeria-postcode-api.md`](../integrations/nigeria-postcode-api.md) §3.3.

### 4.5 App-store policy — shapes the Profile/Subscription screen

- **Apple.** If the app lets users buy digital subscriptions it must use in-app purchase (guideline 3.1.1). The brief shows subscription _status_ and "billing information", not purchase. The safe pattern is guideline **3.1.3(f)**: a _free stand-alone companion to a paid web-based tool_ may skip IAP **provided there is no purchasing inside the app and no calls to action to purchase outside the app** — so no "Subscribe/Renew" buttons or pay-on-web links on iOS. 3.1.3(b) (multiplatform access) additionally requires the item to also be purchasable via IAP; 3.1.3(c) covers services sold directly to _organisations_ for their members (relevant to association-paid access) but "consumer, single user" sales must use IAP. If the app ever offers **account creation**, 5.1.1(v) requires in-app **account deletion** ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). Keep registration on the web for v1.
- **Google Play.** A **personal** developer account created after 13 Nov 2023 must run a closed test with ≥12 testers for 14 continuous days before production; **organisation** accounts are exempt ([Play Console help](https://support.google.com/googleplay/android-developer/answer/14151465)). Register under TwoNode's organisation account; Plan B's schedule has no store-review or account-setup time.
- Both stores require a privacy policy and data-safety/privacy disclosures; surveyor data (names, SURCON numbers, plan locations) is personal data under the Nigeria Data Protection Act 2023.

### 4.6 Backend gaps Plan B doesn't list

1. **Mobile auth surface** (§3) with re-rotation, device sessions, version gate.
2. **Locality/LGA search** (§2).
3. **Geocoding** and **basemap/imagery** providers (§4.4).
4. **Viewport/"near me" plans endpoint** if map browsing is meant to go beyond "my plans" (§2: JSONB, no spatial index). For own plans, a `GET plans/map` that returns `{id, planNumber, status, simplifiedGeometry, centroid}` is enough.
5. **A derived `displayStatus`** shared by web and mobile for batch/plan rows ("Ready for Physical Submission", "Surcon, Account Approved", …) — the brief says these "should reflect the actual workflow"; today they must be computed from `redCopyStatus`, `physicalCopySubmitted`, and the six stage statuses. Define once, test once. **Built 2026-10-19 (#500):** `surfboard/utils/planStatus.ts`.
6. **Push**: device-token table, platform (APNs/FCM) senders, event hooks where queries/batch moves are written, notification preferences. Existing notifications are in-app/email/WhatsApp (`notificationService`, `lib/whatsapp/*`).
7. **Rate-limit keys** for mobile (§3.3).

### 4.7 Details Plan B gets right but under-specifies

- **Physical-copy action** is idempotent server-side (`physicalCopySubmitted:false` filter), so safe to retry; at an intake desk with bad signal the app should queue and retry the tap rather than error, and show the server-confirmed result.
- **Subscription gating on mobile.** Reads (plans, map, queried, batches) are available to unsubscribed users under the Shared Access model; capability actions are gated by `requireActiveSubscription`. Confirm whether the physical-copy submission should be gated (today it is `USER`-role only).
- **Association sponsorship** ("Sponsored by …") is a read of the subscription history source described in [`../surfboard/association-subscription.md`](../surfboard/association-subscription.md) §4.10 — a dependency, not a separate build.

### 4.8 Scope creep and the timeline

- **Offline SQLite/WatermelonDB caching** is not in the brief ("Access. Monitor. Act." — online lookups and light actions). It is also constrained by §4.4 (can't pre-seed OSM tiles). Defer; if "see my plans without signal" matters, start with a persisted read-through cache of plan lists/geometry, not a sync engine.
- **Push and biometrics** are sensible phase-2 items, but neither is in the brief; keep them out of the MVP definition.
- **Timeline.** The Gantt chart starts the day after it was written, allots 5 days to the schema and 10 to MapLibre + omnibar, and has no time for: store accounts, privacy disclosures, review cycles, tile/imagery procurement, the monorepo extraction, or the mobile auth work in §3. Treat dates as unestimated; size by phase (below).

### 5.3 Definition of "ready for physical submission" (to settle with the product owner)

Server rule today: `redCopyStatus = SUBMITTED` ∧ `physicalCopySubmitted = false` ∧ not deleted. The brief shows it alongside _"Surcon, Account Approved"_, which are per-stage approval statuses — confirm whether "ready" also requires specific stage approvals, and encode the answer in one server-side function used by both clients.
